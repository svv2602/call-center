# Runbook: Отказ LLM-провайдера на живом звонке

**Дата создания:** 2026-11-20
**Владелец:** DevOps / SRE
**Приоритет:** HIGH (квота и ключ — CRITICAL)

## Описание

Каждая реплика бота — запрос к LLM-провайдеру. Обе сети закреплены за одной моделью (`tenants.config.agent_provider_override`). Если провайдер не отвечает, клиент ждёт в тишине до 45 секунд и слышит «Перепрошую, не почула…».

Три правила Prometheus (`prometheus/alerts.yml`) сообщают об этом в Telegram. Трафик — единицы звонков в день, поэтому все три срабатывают **на одно событие**, без порога по частоте, и гаснут сами через 15 минут после последнего события. Погасшее оповещение не означает, что провайдер восстановился.

| Оповещение | Уровень | Что произошло |
|---|---|---|
| `LLMProviderFailure` | high | Провайдер отказал на задаче `agent` (ход живого звонка, прощание, песочница админки) |
| `LLMProviderQuotaOrAuth` | critical | Причина отказа — `quota` или `auth`, на любой задаче. Без человека не пройдёт |
| `LLMFallbackActivated` | medium | Звонок ответила запасная модель. Причина — в двух правилах выше |

## Симптомы

- Сообщение в Telegram с именем правила, провайдером и причиной.
- Счётчик `callcenter_llm_provider_failures_total{provider, task, reason}` растёт. Причины — закрытый список:

| `reason` | Что это | Что делать |
|---|---|---|
| `quota` | Закончился баланс (HTTP 402; у OpenAI — 429 с `insufficient_quota`; у Anthropic — 400 «credit balance is too low») | Пополнить счёт провайдера |
| `auth` | Ключ отклонён (401 / 403) | Заменить ключ в `.env`, пересоздать `call-processor` |
| `rate_limit` | Превышен лимит запросов (429) | Обычно проходит само; если повторяется — поднять лимит у провайдера |
| `timeout` | Провайдер не ответил: свой таймаут запроса (35 с) или дедлайн первого события | Проверить статус провайдера и сеть |
| `http_5xx` | Ошибка на стороне провайдера | Проверить статус провайдера |
| `network` | DNS, TLS, обрыв соединения | Проверить сеть и DNS сервера |
| `other` | Всё остальное, включая вызовы, отклонённые открытым предохранителем | Смотреть лог (ниже) |

- В логе `call-processor`: `Stream provider <ключ> failed for task agent: reason=…, status=…`.
- Перебивание клиента (отмена хода) отказом **не считается** и оповещение не поднимает.

## Диагностика

### 1. Какой провайдер и почему

```bash
# Отказы за последний час по провайдеру, задаче и причине
curl -s 'http://localhost:9090/api/v1/query' \
  --data-urlencode 'query=sum by (provider, task, reason) (increase(callcenter_llm_provider_failures_total[1h])) > 0' | jq '.data.result'

# Строки лога с причиной и HTTP-статусом
docker compose logs --since 1h call-processor | grep -E "failed for task .*reason="
```

### 2. Была ли запасная модель

```bash
# Переключения: с какого провайдера на какой
curl -s 'http://localhost:9090/api/v1/query' \
  --data-urlencode 'query=sum by (from_provider, to_provider, task) (increase(callcenter_llm_fallbacks_total[1h])) > 0' | jq '.data.result'

# Цепочка задачи agent и закрепление сетей
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:8080/admin/llm/config | jq '.tasks.agent'
docker compose exec -T postgres psql -U callcenter -d callcenter -c \
  "SELECT slug, config->>'agent_provider_override' FROM tenants;"
```

Переключение считается в момент первого события запасной модели, поэтому в счёт попадает и ответ, который клиент перебил.

### 3. Жив ли провайдер сейчас

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://localhost:8080/admin/llm/providers/<ключ>/test | jq
```

### 4. Включены ли флаги защиты

```bash
docker compose exec -T call-processor env | grep -E "^FF_LLM_|^FF_STREAMING_LLM"
```

## Флаги

Все три выключены по умолчанию. Откат каждого — убрать переменную и пересоздать `call-processor` (только при `callcenter_active_calls == 0`, с `--force-recreate`).

| Переменная | Что делает |
|---|---|
| `FF_LLM_OVERRIDE_FALLBACK=true` | Живой звонок сети, закреплённой за одной моделью, при её отказе идёт дальше по цепочке задачи `agent`. В потоке — только пока клиент ничего не услышал: начало ответа дважды не звучит. Песочница, голдсет и реплеи остаются на заданной модели |
| `FF_LLM_FIRST_EVENT_TIMEOUT_SEC=<секунды>` | Сколько ждать первого события от провайдера, прежде чем считать его отказавшим. Действует только вместе с первым флагом. `0` — без дедлайна. Значение выбирать по p99 латентности с прода, не больше 15 |
| `FF_LLM_OUTAGE_TRANSFER=true` | Ход, на который не ответил ни один провайдер, заканчивается фразой «…Спробую з'єднати вас з оператором» и попыткой перевода. Не принят перевод — клиент слышит, что соединить не удалось. Одна попытка на звонок. **Не включать, пока владелец не утвердил тексты фраз** (`LLM_OUTAGE_TRANSFER_TEXT`, `LLM_OUTAGE_TRANSFER_FAILED_TEXT` в `src/agent/prompts.py`) |

Без первого флага запасной модели у закреплённой сети нет: цепочка состоит из одного провайдера.

## Решение

1. **`quota` / `auth`** — пополнить счёт или заменить ключ. Пока это не сделано, все звонки сети остаются без ответа (при выключенном `FF_LLM_OVERRIDE_FALLBACK`) или идут на запасную модель.
2. **Провайдер лежит, запасная модель не включена** — включить `FF_LLM_OVERRIDE_FALLBACK` либо временно сменить закрепление сети на живого провайдера (`tenants.config.agent_provider_override`).
3. **Открыт предохранитель** (причина `other`, в логе `CircuitBreakerError`) — он закрывается сам через 30 секунд после 5 отказов подряд; если провайдер восстановился, ничего делать не нужно.
4. **Оповещение пришло из песочницы админки** — провайдер тот же, что обслуживает звонки: проверить его (шаг 3 диагностики), а не отмахиваться.

После восстановления: счётчик отказов перестал расти, тестовый звонок получает ответ.

## Проверка переводов по отказу

```bash
curl -s 'http://localhost:9090/api/v1/query' \
  --data-urlencode 'query=sum by (outcome, cause) (increase(callcenter_llm_outage_transfers_total[24h])) > 0' | jq '.data.result'
```

`outcome="transferred"` — оператор получил звонок; `transfer_failed` — перевод не принят (нерабочее время, нет AMI), клиент остался с ботом. В `calls.transfer_reason` такие переводы идут с причиной `llm_outage`.

## Чего оповещения не видят

- Отказы LLM в воркерах Celery (оценка качества, обработка статей): у воркера свой роутер, его метрики Prometheus не собирает.
- Отказ классификатора намерений (`task="intent_classifier"`) правило `LLMProviderFailure` не поднимает; `quota` и `auth` ловятся на любой задаче.
- `LLMFallbackActivated` — вспомогательное правило: рестарт процесса и новое переключение в пределах 15 минут могут дать пропуск, а провал сбора метрик 15 минут назад — ложное срабатывание уровня medium. У двух правил по счётчику отказов этих дыр нет: его ряды выставляются нулями при старте.

## Эскалация

Провайдер недоступен дольше 30 минут и запасная модель не помогает — сообщить владельцу проекта и перевести входящие на операторов средствами Asterisk.
