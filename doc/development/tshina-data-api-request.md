# Запрос к команде tshina: API выгрузки данных для голосового бота

**От:** команда Call Center AI (голосовой бот сетей Твоя Шина и Про Колесо)
**Дата:** 2026-09-29

## Зачем

Голосовой бот консультирует покупателей по шинам и дискам. Три набора данных у вас свежее и полнее, чем у нас:

1. **EU-этикетки шин** — бот сравнивает модели по классам сцепления на мокрой дороге, экономии топлива и шуму («чим Turanza 6 краща за T005?»).
2. **Тесты шин** (ADAC и др.) — второй источник для сравнения моделей.
3. **Справочник авто** — штатные размеры шин и дисков по марке, модели, году.

Сейчас мы перенесли все три набора **разово из локальной копии** вашей базы (2026-09-28). Данные устаревают: вы дополняете этикетки из EPREL, снимаете конфликтные, обновляете справочник. Просим три эндпоинта только на чтение, чтобы мы забирали изменения по расписанию, раз в сутки ночью.

Ключи уже общие, сопоставление не нужно: код товара 1С (`catalog_products.sku`), код модели 1С (`catalog_product_models.sync1c_model_id`), id справочника car2 (`car_directory_*.id`).

## Общие требования (для всех трёх эндпоинтов)

- **Только чтение**, `GET`, JSON в UTF-8, версия в пути: `/api/v1/…`.
- **Авторизация:** статический токен `Authorization: Bearer <token>`. Желательно ещё ограничение по IP. Токен и IP передадим отдельно.
- **Инкрементальная выгрузка:** параметр `updated_since=<ISO-8601 UTC>` отдаёт всё, что создано, изменено **или удалено** после отметки. Удалённая запись приходит с `"deleted": true` и ключом (остальные поля можно не заполнять). Без удалений у нас останутся данные, которые вы сняли. Например, этикетки, снятые `--fix-conflicts`.
- **Полный снимок:** без `updated_since` — все живые записи. Раз в неделю мы делаем по нему сверку.
- **Пагинация курсором:** `cursor` + `limit` (по умолчанию 1000, максимум 5000). В ответе `next_cursor` (`null` на последней странице). Курсор должен быть стабилен, пока идёт обход: запись не пропадает и не дублируется, если во время обхода её изменили.
- **Отметка сервера:** каждый ответ содержит `server_time` (UTC). Следующий инкремент мы запрашиваем с `updated_since` = `server_time` **первой** страницы предыдущего обхода, поэтому пограничные изменения не теряются. Повтор записи для нас безопасен (upsert).
- **Время** — везде UTC, ISO-8601 с `Z`.
- **Ошибки:** `401` — токен, `400` — параметры (с текстом ошибки), `429` — лимит (с `Retry-After`), `5xx` — мы повторим позже. Недоступность API у нас ничего не ломает: остаются последние данные.
- **Нагрузка:** раз в сутки инкремент, раз в неделю полный снимок, последовательно, не чаще 5 запросов в секунду.
- **Типы:** числа — числами, классы — одной заглавной латинской буквой, «нет значения» — `null` (не пустая строка и не `0`).

Формат ответа (общий):

```json
{
  "items": [ … ],
  "next_cursor": "eyJpZCI6MTIzfQ",
  "server_time": "2026-09-29T02:00:00Z"
}
```

## 1. EU-этикетки шин

`GET /api/v1/eu-labels?updated_since=…&cursor=…&limit=…`

Источник у вас: `catalog_product_euro_labels` + `catalog_products.sku`. Сейчас 26 819 записей.

```json
{
  "sku": "00000044795",
  "energy_class": "B",
  "wet_grip_class": "C",
  "noise_db": 71,
  "noise_class": "B",
  "eprel_number": "2487145",
  "updated_at": "2026-09-28T14:32:37Z",
  "deleted": false
}
```

| Поле | Тип | Правило |
|---|---|---|
| `sku` | string | код товара 1С (`catalog_products.sku`), ключ |
| `energy_class` | `A`–`G` | класс экономии топлива (у вас колонка `energy_сlass` — с кириллической «с») |
| `wet_grip_class` | `A`–`G` | сцепление на мокрой дороге |
| `noise_db` | int | внешний шум качения, дБ (сейчас строка `external_rolling_noise_value`) |
| `noise_class` | `A`–`C` | класс шума |
| `eprel_number` | string \| null | номер регистрации EPREL |
| `updated_at` | ISO-8601 | когда запись последний раз изменилась |
| `deleted` | bool | `true` — этикетка снята (конфликт EPREL и т. п.) |

## 2. Тесты шин

`GET /api/v1/tire-tests?updated_since=…&cursor=…&limit=…`

Источник у вас: `catalog_tire_tests`, `…_translations`, `…_sizes`, `…_placements`, `…_criteria_scores`, `…_sources`, `…_source_ratings`. Сейчас 35 тестов, 415 мест. Одна запись — один тест со всеми местами. Изменение любого места поднимает `updated_at` теста.

```json
{
  "id": 17,
  "source": {"key": "adac", "title": "ADAC", "scale_min": 0.5, "scale_max": 5.5, "higher_is_better": false},  // значения — для примера, из catalog_tire_test_sources
  "year": 2024,
  "season": "summer",
  "test_date": "2024-02-20",
  "size": {"width": 215, "height": 55, "diameter": 17, "raw": "215/55 R17"},
  "notes": {"ua": "…", "ru": "…"},
  "placements": [
    {
      "place": 1,
      "brand": "Bridgestone",
      "model": "Turanza 6",
      "model_1c_id": "000012345",
      "rating": {"code": "gut", "ua": "Добре", "ru": "Хорошо", "en": "Good"},
      "notes": "…",
      "criteria": [
        {"criterion": "wet", "score_raw": 2.1, "score_normalized": 78, "rank": 3}
      ]
    }
  ],
  "updated_at": "2026-09-20T10:00:00Z",
  "deleted": false

```

| Поле | Правило |
|---|---|
| `placements[].model_1c_id` | `catalog_product_models.sync1c_model_id` модели, к которой вы привязали место (`product_model_id`). Если привязки нет — `null`, и тогда обязательны `brand`/`model` (ваши `brand_raw`/`model_raw`) |
| `season` | `summer` / `winter` / `all_season` |
| `size.diameter` | число без «R» |
| `criteria` | сейчас пусто (`catalog_tire_test_criteria_scores` = 0 строк) — отдавайте `[]`, пока не заполните |
| `rating` | код и подписи из `catalog_tire_test_source_ratings` |

## 3. Справочник авто

Пять ресурсов, ключи — id car2, общие с нашей базой:

```
GET /api/v1/vehicles/brands?updated_since=…&cursor=…&limit=…
GET /api/v1/vehicles/models?…
GET /api/v1/vehicles/modifications?…
GET /api/v1/vehicles/tire-sizes?…
GET /api/v1/vehicles/disk-sizes?…
```

Источник у вас: `car_directory_brands` (231), `…_models` (6 101), `…_modifications` (317 612), `…_tire_sizes` (1 246 409), `…_disk_sizes` (1 188 696). Размеров больше миллиона, поэтому инкремент по `updated_since` здесь важнее всего. Полный снимок постранично, по `limit=5000`.

```json
// brands
{"id": 228, "name": "Avatr", "updated_at": "…", "deleted": false}
// models
{"id": 5906, "brand_id": 228, "name": "11", "updated_at": "…", "deleted": false}
// modifications
{"id": 308706, "model_id": 5906, "year": 2024, "name": "2.0 TGDI",
 "pcd": 108.0, "bolt_count": 5, "dia": 65.1, "bolt_size": "M14 x 1.5",
 "updated_at": "…", "deleted": false}
// tire-sizes
{"id": 3106816, "modification_id": 308706, "width": 235, "height": 60, "diameter": 18,
 "type": 1, "axle": 0, "axle_group": null, "updated_at": "…", "deleted": false}
// disk-sizes
{"id": 3106816, "modification_id": 308706, "width": 7.0, "diameter": 17, "et": 45.0,
 "type": 1, "axle": 0, "axle_group": null, "updated_at": "…", "deleted": false}
```

**Правила значений.** На каждое из них мы наткнулись при ручном импорте:

| Поле | Сейчас у вас | Нужно в API |
|---|---|---|
| `diameter` | строка `"R16"` | число `16` |
| `width`, `height`, `et`, `pcd`, `dia` | строки | числа (`et` может быть `null`) |
| `axle_group` | `0` там, где значения нет | `null`, если группы нет (`0` — только реальная группа 0) |
| `et` | пустая строка там, где значения нет | `null` |
| `year` | `YEAR` | целое число |
| `type` | tinyint | как есть: 1 — штатный, 2 — нештатный (тюнинг), как в исходном car2 |
| `axle` | tinyint | как есть: 0 — обе оси, 1 — передняя, 2 — задняя |

**Порядок и целостность.** Мы применяем ресурсы в порядке brands → models → modifications → sizes. Удаление родителя должно приходить вместе с удалениями его детей (или дети — раньше), чтобы у нас не оставались размеры без модификации.

**Данные, которые мы у себя пропускаем** (вам ничего менять не нужно, сообщаем для сведения):
- марки-дубли Hongqi (дублирует Red Flag) и KG Mobility (дублирует Ssang Yong): у нас они ломают распознавание моделей Tivoli, Rexton, Torres;
- модели с названием марки (мусор Alpine в исходном car2).

## Вопросы к вам

1. Сроки и кто контакт с вашей стороны.
2. Можете ли отдавать удаления (`deleted: true`)? Если нет — перейдём на еженедельный полный снимок и будем удалять у себя всё, чего в нём нет.
3. Есть ли у вас `updated_at` на всех таблицах справочника, обновляемый при импорте CSV? Если импорт пересоздаёт строки целиком, инкремент будет отдавать всё — тогда для справочника достаточно полного снимка раз в неделю.
4. Планируете ли заполнять `catalog_tire_test_criteria_scores`? Критерии (мокрая дорога, сухая, шум, износ) нам особенно полезны для сравнения.

## Что делаем мы, когда эндпоинты появятся

- Ночная задача (Celery beat): инкремент по трём наборам с отметки `server_time` прошлого обхода, upsert. Строка принимается целиком или отклоняется: классы проверяются по шкале ЕС, числа — по диапазонам.
- Раз в неделю — полный снимок и сверка, отчёт о расхождениях.
- Метрика «возраст последней успешной синхронизации» с алертом, если данные старше 2 суток.
- Клиент напишем заранее на моке ответа из этого документа и включим, когда API будет доступен.
