# Рекомендации по следующим шагам для улучшения STT

**Дата:** 2026-08-05  
**Контекст:** продолжение исследования `stt_models_research.md`. Цель — улучшить распознавание украинской/русской речи, городов, брендов шин, размеров и номерных знаков без повторения уже проверенных тупиковых комбинаций Google STT v2.

---

## 1. Перепроверить `chirp_3` в мультирегионе `eu`

Самый перспективный следующий эксперимент — `chirp_3 + eu + uk-UA/ru-RU + speech adaptation`.

Причина: актуальная документация Google указывает, что `chirp_3` доступен в мультирегионах `eu` и `us`, а таблица поддерживаемых языков показывает для `chirp_3` в `eu` поддержку `Model adaptation`. Это потенциально закрывает прежнее фундаментальное противоречие:

```text
uk-UA + ru-RU multilingual  -> eu/global/us
speech adaptation           -> chirp-модели
chirp_3                     -> eu/us
```

Рекомендуемый тестовый конфиг:

```env
GOOGLE_STT_MODEL=chirp_3
GOOGLE_STT_LOCATION=eu
GOOGLE_STT_ALTERNATIVE_LANGUAGES=ru-RU
GOOGLE_STT_ENDPOINTING_SENSITIVITY=STANDARD
GOOGLE_STT_SPEECH_END_TIMEOUT_MS=0
```

Критерии успеха:

- attempt 1 с phrase hints не падает;
- `uk-UA + ru-RU` принимаются одновременно;
- нет фрагментации финалов уровня `chirp_2`;
- WER и ошибки по сущностям лучше baseline `latest_long/global`.

Перед боевым тестом лучше расширить `scripts/stt_ab_test.py`, чтобы он сравнивал:

- `latest_long/global`, `uk-UA + ru-RU`, без adaptation;
- `chirp_3/eu`, `uk-UA + ru-RU`, без adaptation;
- `chirp_3/eu`, `uk-UA + ru-RU`, с phrase hints и boost-фразами.

## 2. Убрать failed retry как постоянный режим

Сейчас baseline работает так:

```text
attempt 1: latest_long/global + adaptation -> FAIL
attempt 2: latest_long/global без adaptation -> OK
```

Это функционально терпимо, но плохо как постоянный режим:

- лишняя ошибка на каждый звонок;
- шум в логах;
- потенциальная задержка старта распознавания;
- риск, что настоящие STT-проблемы будут теряться среди ожидаемых ошибок.

Рекомендация: добавить capability-probe/cache.

Идея:

1. При старте сервиса или первом звонке проверить текущую комбинацию `model/location/language_codes/adaptation`.
2. Если Google возвращает "adaptation not supported", сохранить это в памяти или Redis.
3. Для следующих звонков не отправлять hints в STT, пока конфиг не изменится.
4. Admin UI продолжает показывать баннер, но pipeline больше не делает заведомо падающий attempt.

Это не улучшит качество распознавания напрямую, но сделает систему чище и надежнее.

## 3. Решать фрагментацию финалов своим utterance gate

Для `chirp_2` проблема была не только в модели, а в поведении streaming final results:

```text
final 1 -> предварительная версия
final 2 -> исправленная версия
final 3 -> еще одна исправленная версия
```

Pipeline обрабатывает каждый final как новый ход пользователя, из-за чего бот отвечает 2-3 раза.

Рекомендация: добавить слой `utterance gate` перед передачей текста в LLM.

Поведение:

- хранить final-фрагменты в окне до 8-12 секунд, если новые finals похожи на предыдущие;
- считать similarity между предыдущим и новым final;
- если новый final выглядит как revision той же фразы, заменять старую версию, а не создавать новый ход;
- выбирать лучшую версию по комбинации признаков:
  - более поздний final;
  - больше слов;
  - выше confidence;
  - содержит больше доменных сущностей;
- если бот уже ответил, подавлять следующий final как revision, если similarity высокая и нет нового интента;
- для коротких реплик типа "так", "ні", "добре" оставить быстрый путь без длинного ожидания.

Это позволит безопаснее тестировать `chirp_2`/`chirp_3`, даже если Google продолжит отдавать revised finals.

## 4. Усилить deterministic parsers для доменных сущностей

STT не обязан идеально распознавать структурированные сущности. Для шинного call center выгоднее усиливать постобработку:

### Размеры шин

Нужно нормализовать варианты:

```text
205/55 R16
205 55 16
двісті п'ять п'ятдесят шістнадцять
двести пять пятьдесят шестнадцать
```

Результат должен приводиться к канонической форме `205/55 R16`.

### Номерные знаки

Рекомендуется state machine:

```text
региональный префикс -> 4 цифры -> 2 буквы
```

С whitelist украинских префиксов и допустимых букв. Это должно работать лучше, чем общие regex-замены после STT.

### Города

Использовать fuzzy match по whitelist:

```text
Дніпро / Днепр
Запоріжжя / Запорожье
Харків / Харьков
Київ / Киев
```

С ограничением по контексту, чтобы не исправлять обычные слова на города вне сценария адреса/доставки/наличия.

### Бренды и модели шин

Поддерживать phonetic aliases:

```text
Michelin -> Мішлен, Мічелін, Мишлен
Bridgestone -> Бріджстоун, Бриджстоун
Continental -> Контіненталь, Континенталь
```

Это естественное продолжение существующих `phrase_hints`, `stt_corrections` и `numeral_parser`.

## 5. Whisper тестировать как параллельного кандидата

`src/stt/whisper_stt.py` уже реализован как feature-flag провайдер, но перед включением в бой его нужно оценить отдельно.

Риски текущей реализации:

- аудио режется по фиксированному порогу буфера, а не по настоящей VAD-границе;
- нет полноценной streaming-семантики;
- latency может быть выше Google STT;
- качество на телефонном 8 kHz аудио нужно измерять на реальных звонках, а не предполагать.

Рекомендация:

1. Добавить Whisper в offline A/B тест.
2. Тестировать Faster-Whisper `large-v3` и `large-v3-turbo`.
3. Использовать VAD по тишине, например Silero/WebRTC VAD, вместо фиксированных 2 секунд.
4. Сравнивать не только WER, но и entity accuracy:
   - города;
   - размеры шин;
   - бренды;
   - номерные знаки;
   - даты/время записи.

Whisper стоит рассматривать как второй provider под feature flag, а не как мгновенную замену Google.

## 6. Метрики для принятия решения

Для выбора STT-провайдера одного общего WER мало. Нужны прикладные метрики:

| Метрика | Зачем нужна |
|---|---|
| WER общий | Базовое качество распознавания |
| WER uk-UA | Не потерять украинский основной сценарий |
| WER ru-RU | Не ухудшить русскоязычных клиентов |
| Entity accuracy: tire size | Критично для подбора шин |
| Entity accuracy: city | Критично для доставки/наличия |
| Entity accuracy: plate | Критично для записи/идентификации авто |
| Duplicate bot replies per call | Проверка фрагментации финалов |
| STT first-final latency | Влияет на ощущение диалога |
| STT error rate | Надежность в бою |

Минимальный набор для A/B:

```text
100-200 реальных размеченных фрагментов:
  70% украинский
  30% русский
  отдельные теги: city, tire_size, brand, plate, date
```

## Приоритетный план

1. Расширить `scripts/stt_ab_test.py` под `chirp_3/eu` и adaptation.
2. Прогнать offline A/B на размеченных звонках.
3. Если `chirp_3/eu + adaptation` работает и лучше baseline — включить ограниченный боевой canary.
4. Если `chirp_3` дает фрагментацию — реализовать utterance gate.
5. Параллельно усилить deterministic parsers для размеров, номеров, городов и брендов.
6. После этого добавить Whisper в A/B как альтернативного provider.

Главная рекомендация: не ждать обновления Google вслепую. Сначала проверить `chirp_3/eu + uk-UA/ru-RU + adaptation`, потому что это наиболее чистый путь к работающим phrase hints без отказа от мультиязычности.
